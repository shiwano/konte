How konte turns `direction.ts` into two verdicts a person and the spend gate act on: a machine check over the arc and rosters, and a human acceptance recorded per reviewable part. `direction-check.ts` is the DSL-free engine; `direction.ts` the doctor + gate on top; `direction-hash.ts` and `direction-acceptance.ts` own the per-part hashing and the human verdict. All of it keys off a part's **address** (`direction:<field-path>`) — both the state key and the review target.

## The arc engine and finding classes

`checkArc` (`direction-check.ts`) is the one generic engine, reused at every scale of the arc tree — a run of shots, a run of sequences, a run of runs — generic over the role string. It reads each item's dramatic `fn` off the matched lens beat (no global role vocabulary) and reports `DirectionFinding`s; it never throws and never decides severity. `direction.ts` `walkArcTree` runs it once per node with a resolvable lens (a leaf's shots, a branch's meta-arc over children) and folds each finding against that node's `waivers` bag.

## Asides

A leaf's `shots` array holds three kinds (the third, `GraphicShot`, below). `NarrativeShot` is the default (`role`/`action`/`setup`, `kind` omitted); `AsideShot` (`kind: "aside"`) is a shot that occupies the clock without being part of the arc — a title card, an eyecatch, an OP — and carries `{ id, label, duration, telop? }` and nothing else.

**The split is between the arc's two questions, and it lives in `buildArcNode`.** `items` holds the narrative shots only, so every role, `fn`, framing, adjacency and share check skips an aside — and `nodeDuration` sums `items`, so an aside's span is outside the share denominator at every scale. `coverageIds` holds every shot, and `checkArc` reads it for `unrealized` / `stage-order-mismatch` alone, so a declared aside nobody realizes is still caught at export. Do not collapse the two: filtering asides out of `items` without `coverageIds` silently drops coverage as well.

`collectArcShots` (`direction.ts`) is every arc shot, narrative and graphic, and is the default reader; `collectCameraShots` is the narrative ones, for the readers of `setup` / `lineup` / `join`; `collectShots` is every shot, for the clock, the id namespace and the stage's coverage. Structural: `aside-empty-label` and `run-aside-shot` (a continuity run binds backgrounds, and an aside has none).

An aside is a reviewable part like any other — `projectShotShape` hashes its `kind` and `duration`, `projectShot` adds its label, and `directionPartContents` emits a `kind: "aside"` content with the arc's columns absent. `directionShotCascadeTargets` gives it **only its own part**: no setup to sign off, and no act chain.

`ConstrainIds` (`dsl/direction.ts`) settles six in the type instead, each blamed in the field that was written: `off-grid-duration` (asides outside it, as in `checkDurations`), `empty-synopsis` (`action` / `synopsis`), `lineup-vacuous`, `unexpected-script`, `join-impossible` (`ConstrainJoin` / `ConstrainCutinJoin` read the shot before on the clock off `DirectionShotTuple`) and `lens-role-mismatch` (`LensRolesOf` reads the node's own `lens`; a child node's `role` answers to its PARENT's, and `defineLens` widens so a custom lens passes through). Write the `DirectionViolation<M>` inline — behind an alias the compiler prints the alias name, not the advice. A widened value passes through to the finding.

Only a direction-LOCAL demand that fires on a value WRITTEN, never on one not yet written, belongs here: the startup type-check aborts every command (`arch-cli-guide`), so a demand naming another stage's file, or one an unfinished direction fails, stops `preview direction` itself.

A waivable finding has a **class** (`DirectionFindingClass`): `arc` | `pacing` | `stage` | `completeness` | `characters` | `props` | `locations` | `setups` | `typesetting`. `FINDING_CLASS` maps each code; `classifyDirectionFinding` reads it. Two orthogonal things gate on the class:

- **Deferral** — `reportableDirectionFindings` drops the `DEFERRED_UNTIL_ACCEPTED` classes (all four rosters) while the direction is not yet accepted: they point at post-acceptance roster wiring and would derail the direction review. Every reporting/gating surface (doctor, preview, spend gate) passes findings through it.
- **Gating scope** — `gatedClasses(command, stage)`: `generate`/`reroll` gate on every class but `completeness`; only a video `export` adds it (unrealized shots). `assertDirectionGate` throws `DIRECTION_CHECK_FAILED` when the scoped, unwaived, reportable subset is non-empty.

A **structural error** (`DirectionStructureError`, codes in `DirectionErrorCode`) is a definition bug, never waivable and always fatal — kept apart from the waivable finding set. `validateDirectionStructure` produces them (empty direction, duplicate id, unknown lens, payoff-not-in-beats, the per-roster `character-*`/`prop-*`/`location-*`/`landmark-*`/`setup-*`/`holds-*` errors, `reference-id-conflict`, `script-*`).

A waiver is keyed `<code>` or `<code>_<subject>` (`directionWaiverKey`); the first `_` splits it back apart (no code contains one). Stale-waiver detection runs per bag over only the classes a pass actually evaluated, so a direction-only pass (doctor) never mislabels a still-valid stage/completeness waiver.

## Graphic shots and cutins

A `GraphicShot` (`kind: "graphic"`) is an arc shot with no camera: it stays in `items` with `framing` / `location` / `axis` undefined, which every spatial check already passes over, and since it stays there the shots either side of it are not adjacent. The main lane's `axisCuts` and seams break on it as on an aside.

A `cutin` is a second camera frame over an arc shot, so **the camera readers take frames, not shots**: `collectShotFrames` yields a shot's main frame then its cutin (`lane`), and `setup-unknown`, the lineup errors, the plate counts and `listSetupAnchorGaps` read frames. `joinBoundaries` pairs each frame with the previous clock shot's frame in the same lane, so the join errors, `panelSeams` and a cutin's `axisCuts` are per lane. `checkLineups` keeps one accumulation per place across both lanes, empties every place when either frame of a shot jumps, and reads a seam against the previous entry of the same `frame`; every board reading carries `lane`. A cutin's subject is `<shotId>.cutin`, so neither frame's waiver cancels the other's. `cutin.setup` / `join` ride `projectShotShape`, its lineup `projectShot`.

## The three anchored rosters

`characters` (required), `props` (optional) and `locations` (required, non-empty) are `Record<id, { name, description }>`, each id anchored to a `reference:<id>` asset. A character adds a required `promptDepiction` and an optional `voice` (see **Casting voices**); a location a required, non-empty `landmarks` roster (see **The fourth roster**). One generalized helper, `checkAnchoredEntities` (`direction-check.ts`), sits behind the thin `checkCharacters` / `checkProps` / `checkLocations` wrappers, producing two exact-match findings per roster:

- `<noun>-unreferenced` — the `id` has no matching exposed `reference:<id>` asset.
- `unused-<noun>` — the entity is used by no shot. What "used" means splits the rosters:
  - **character / prop** — the `name` is a literal substring of some shot `action`. One-directional: the reverse (a prose noun with no declared entity) needs NL parsing to catch. A character with a `{ character }` script line is exempt (passed as the "always used" set); a prop never speaks, so it gets an empty set.
  - **location** — a shot reaches its location through its `setup`, and "used" is exact id membership in the set of locations the used setups are set in (passed as the always-used set, with an empty `actions` list).

The cross-reference runs only when the caller supplies `referenceAssetNames` (`checkDirection`), so the roster classes are silent — and their waivers never flagged stale — when the reference stage can't be read.

All three rosters share the `reference:<id>` namespace, so `validateDirectionStructure` rejects an id declared in two of them (`reference-id-conflict`). Landmark ids join no arm of it — nothing exposes `reference:<landmarkId>` — but the direction keeps ONE id space, so a landmark colliding with a roster id or with another place's landmark is `landmark-id-conflict`.

`promptDepiction` is what a prompt calls a thing by, required on a character and on a landmark — a noun **the model can draw**, where `name` is the piece's word for it. It carries the least that separates this one from the rest. konte only ever scans for it and never writes it into a prompt. It has its own namespace, over the characters and every place's landmarks — a panel's prompt chain carries its plate's sentence too. A noun containing another is a pair neither naming scan separates: `prompt-depiction-conflict`, keyed by the contained entry.

## The fourth roster: setups

`setups` (required, non-empty) is `Record<id, { name, description, location, framing, holds, within? }>`; every shot names one in its required `setup` field and carries neither `framing` nor `location`.

`DirectionIndex` resolves both, so every reader — the shot contexts, `buildArcNode`'s arc items — sees a resolved value; an unresolvable one throws in `stageShotContext`, since a stage's builds run before the gate. `Setup` and `Landmark` are exported from **both** `dsl/index.ts` and `dsl/template-entry.ts`.

A **landmark** is `{ name, promptDepiction, description }` under a location's `landmarks` roster: what only that place has. It anchors on no `reference:<id>` of its own — its setup's plate is the frame's anchor. `holds` is the frame's contents: landmark ids of its own location, left to right, required and non-empty unless `framing` is `"insert"`. A shot never restates it. `ConstrainSetupHolds` reaches the ids through the setup's own `location` literal and re-blames each element, and asks an empty non-insert tuple for a first element it cannot supply. `landmarks` non-emptiness has no type to state it, so `landmarks-empty` is structural, beside `holds-empty` / `holds-unknown-id`. It reaches no `ctx` — the stage build receives the frame as a plate, and the left-to-right order is the prompt critic's, printed as `inspect --prompts`' `set:` line.

`within` is the camera axis: the setup this frame is a window cut out of, `null` at a root, and a declaration konte never derives — the same shape is as often a reverse or a second axis. `ConstrainSetupWithin` looks the named entry up in `D["setups"]` and blames the `within` position for an unknown id, another `location`, a `framing` not strictly wider (`WiderThan`, `wide` < `medium` < `close`), and any `within` on an `insert`; every widened type passes through to the runtime. `withinErrors` re-checks all four as `within-impossible`, adds `within-cyclic` (only reachable past the type layer), and demands the declaration as `within-undeclared` wherever a strictly wider setup of the same place carries this frame's `holds` as an ordered subsequence. That subsequence is the CANDIDATE test alone — a window may hold a landmark the wider frame was too wide to declare, so a `within` outside the candidate set is legal. `within` rides `projectSetups` and the setup's part hash, not `projectSetupShape`: the window's parent moves neither the size cadence nor the place.

It does not reuse `checkAnchoredEntities`: what realizes a setup is a **plate**, an `animatic:plate.<setupId>` asset declared in `defineAnimatic`'s `plates` callback. So its id joins no arm of `reference-id-conflict` and no `directionReferenceCascadeTargets` / `referenceRosterEntries` loop, a setup is prose implying no spend until the board exists, and `checkSetups` takes `shotsPerSetup` plus the board's state.

Plates are keyed by roster id and returned as `{ image, prompt }` — the picture, and one English sentence of what that frame holds, contents only; `timeline` receives it unchanged. **konte writes no prompt text**: the author writes that sentence into each keyframe's own prompt, in the adapter's notation, which is all `plate-undescribed` reads. Returning files one under a setup; an asset declared and not returned is an intermediate the plates are built from, and may not take a roster id. Being returned makes each a **usage root**, which is what lets `konte generate animatic` bake them while every shot is still a `pendingShot`. `animatic:plate` is an address-scope, so `probe` reads them all in one command.

`checkSetups` emits six. Four per setup, in that order: `unused-setup` (no shot names it), then — for a setup **two or more** shots name — `setup-unrealized` (no plate) or, behind it, `plate-unnested` and `setup-unconsumed` (a plate no developed shot on it builds from). Each is checked only where the one before it is satisfied, which is what makes waiving a setup out of owing a plate waive its shots out of consuming one. All three are one rule — a developed shot reaches its setup's anchor, and the anchor reaches the place (`plate-unanchored`) — at three points. Reach is per shot, not per panel; `setup-unrealized` counts **generated** shots; both anchor findings wait on `reference:<location>` existing; a shot with no generative step is outside all three, and a plate's own exemption is narrower — one that touches no reference at all (a file handed over whole), whatever its chain generates. `axis-unrealized` reads along `within` (see **Join**).

`plate-unnested` is the plate half of `within`: `listSetupNestGaps` (graph.ts) walks the child's plate chain for a **cut** — a `readsPrevPanel` step handed the parent plate as is (`imageInputs`) — or a **window**: an `imageCrop` straight out of the parent plate, or out of the master the parent plate cuts, strictly inside the parent's rectangle. Windows nest by induction; the crop nearest the parent plate is the parent's window. Silent where either plate is absent.

Two more read the roster whole, on a direction-only pass. `setup-indistinct` compares `location`, `framing` and `holds` order, skipping an `insert` (empty `holds`) and blaming the later id so a roster reorder never moves the waiver key. `setup-atomized` is per LOCATION and a share: `ATOMIZED_LOCATION_SHOTS` (8) shots, fewer than half on a shared frame.

A plate's own sentence is the text half of the same rule, and rides the staging class instead (`plate-undescribed`, below) — it is never deferred, so it gates a spend before the direction is accepted.

The board state arrives as `checkDirection`'s `animaticSetups` (`AnimaticSetupState`: `plateIds` + `unconsumedBy` + the two gap lists), undefined meaning "no board yet"; every reader must pass it (`loadAnimaticSetupState`) or the demand is dead. Stale-waiver detection is per class, so the class enters `evaluatedClasses` only WITH it: marking it evaluated without one would call a live `setup-unrealized` waiver stale.

`unconsumedBy` is `listSetupAnchorGaps(...).unanchoredShots` (graph.ts), a walk over the animatic's OWN refs rooted at each developed shot's PANELS and nothing else — the keyframes are what the finding is about. Not the declared pool (an unrendered asset that takes the plate would clear the finding for a keyframe built from nothing) and not `compositionRefs` either, which carries every layer the shot renders: an overlay or a sound that happens to take the plate says nothing about the frame the keyframe was drawn on. A plate reaching a keyframe through a shot asset, a timeline asset or a `shot(…)` chain is found from the panel. Whether the prompt then names that picture is the prompt critic's.

The plate is **not** acceptance-gated (`unacceptedUpstreamDeps` walks self-stage nodes through, left alone) and is **not review work**: no review page shows it on its own, so it is judged inside the panels drawn on it. A plate sits one level below the composition, reached through the KEYFRAME's job provenance rather than named in `compositionRefs`, so accepting the first panel on it cascades onto it. `listReviewableAssetPaths` / `print-status` keep it out of "Needs review" and the accept ratio; `computeExportReadiness` still counts an unbaked or stale one as `generate` work, since the plate pass bakes it while every shot on it is a `pendingShot`. A handoff note may name it (`collectAllAddresses`).

## Lineup: the staging class

Who a frame holds is a direction declaration: a narrative shot's `lineup` names the `characters` ids the frame holds, left to right on screen — a sleeve in frame counts, there is no off-frame axis, and a prop is never lined up. `lineupTo` is the frame at the shot's end, in full and symmetrical with `lineup`, declared wherever the frame changes inside the shot: whoever it leaves out has walked out of frame. Both reach the author as `ctx.lineup` / `ctx.lineupTo` in the stage build, and as a `lineup:` line above each prompt in `inspect --prompts` — the setup's `holds` prints beneath it as `set:`; konte never expands any of them into prompt text. `lineup-vacuous` is a `lineupTo` equal to the `lineup`.

`checkLineups` (`direction-check.ts`) is the whole accumulation: one `Map` of pairs per LOCATION — "a is left of b" plus the shot that said so — walked in direction order. A shot's `lineup` is checked against it (`lineup-flipped`, then `lineup-gap`), then written into it; a `lineupTo` first DROPS the pairs of whoever the opening frame held and it does not, then writes its own. A `join` of `jump-back`/`jump-forward` clears every place.

`skippedBetween` reads the OUTERMOST pair, not each neighbouring one: someone whose place beside the middle of the list was never declared is inside the span anyway. Dropping on `lineupTo` is what makes it need no presence guard — a subject with no pairs stands nowhere, so it is never between anything. `findCycle` after each write is `lineup-inconsistent`; on a ring the place restarts from that shot's exit order, or every later shot repeats it.

`checkStaging` (`direction.ts`) projects the direction into `LineupShot[]` — each shot's location resolved through its setup, undefined filing it under no place; the same walk carries `join`, which `join-lineup-mismatch` reads against the previous shot's `lineupTo ?? lineup` and `checkJoinPins` against `videoPins`. The board half arrives as `stagingStage` (`loadStagingStageState`) on `animaticSetups`' contract — undefined means "no board", so the class enters `evaluatedClasses` only with it. It carries two readings of the same panels in panel order: `listPanelReferenceSlots`, each panel's OWN inputs, read by `checkSlotOrder` (`slot-order-mismatch`: those inputs in an order the shot does not declare); `listPanelReferenceReach`, the CHAIN behind it, read by `checkCharacterAnchors` — one `character-unconsumed` per subject, keyed `<shotId>.<characterId>`, held back for a character with no `reference:<id>` and for a panel that generates nothing.

`panelPrompts` is the fourth reading, `listPanelPromptText`: the positive prompts of a panel and of every step in the chain behind it, read by `checkSubjectNaming` for each lineup subject's `promptDepiction` (`subject-unnamed`). Same panel rule and same shape as `character-unconsumed` — first panel for the `lineup`, last for the `lineupTo`, keyed `<shotId>.<characterId>`, silent on a non-generative panel — since the two are the picture and the text halves of one demand. Matching is a case-blind substring: a noun is found inside "the desk" and a prompt that opens on a subject and goes on with "she" has named them.

`plate-unnamed` is the text half of `plate-undescribed`, off `platePrompts` (the sentence per setup) rather than the panels: `checkPlateNaming` reads each returned plate's sentence for the `promptDepiction` of every landmark its setup's `holds` declares, keyed `<setupId>.<landmarkId>` so a waiver for a landmark out of the crop does not cover the one in it. `checkLandmarkOrder` needs no board at all — it accumulates pairs per location as `checkLineups` does over shots, and emits `landmark-flipped` where two frames of one place disagree about an axis nothing on it can move. Two differences from the shot walk, both because a landmark does not move: it reads the setups sorted BY ID, since a roster is a set whose record order moves no hash and must not decide which frame a waiver key names; and the first frame to state a pair fixes it, where a shot's lineup overwrites — overwriting here would make one waived reverse angle report every frame after it for agreeing with the original.

`plateUses` is the third reading, `listPlateDescriptionUses`: per developed shot on a plated setup, whether any positive prompt ON THE PATH from a panel back to the plate carries the plate's own sentence verbatim — the panel and the intermediates it is derived from that still stand on the plate. Which panel reaches it stays the shot's business, as under `setup-unconsumed`; reading the panel address alone would exempt a resize wrapper over the keyframe that actually took the plate. Off the path is not read: the plate's own generation prompt and its upstream reach the plate from nowhere, and a sibling branch conditions a picture the plate never entered. Presence is all it reads — which input slot the picture arrives in and how the prompt names it are the adapter's grammar, and the prompt critic's. `plate-undescribed` reports it per SETUP — the sentence is the plate's, so one waiver answers for the frame. It takes `setup-unconsumed`'s two exemptions (nothing generative in the chain, the plate not reached at all) plus one of its own: a shot whose path to the plate conditions on no text has no body the sentence could go in.

`lineup` is REQUIRED on a narrative shot (`[]` where the frame holds no one); one reaching the checker without it is `lineup-missing`, a structural error only a computed direction reaches.

The type layer is the first line on the roster: `ConstrainIds` re-blames each lineup element as `SubjectIdOf<D>`. A bad id maps to `LineupSubjectViolation<T>`, an OBJECT not the roster union — a `never` element would collapse the tuple it is intersected with and blame every id in it.

## Join

Whether there is a cut at all is a direction declaration too. A narrative shot's `join` states the boundary INTO it, so the shot after a boundary owns it. Omitted is an ordinary cut with story time running on; `"jump-back"` / `"jump-forward"` are cuts that move story time; `"continuous"` is no cut at all — this shot and the one before it are one unbroken take. The four states are exclusive and exhaustive, so a jump inside a long take is not expressible.

A long take is possible only where the shot before it **on the clock** (asides included) is a narrative shot on the **same setup** — one take is one camera position, so a hold that moves is written as two panels inside one shot. Where it is not, `"continuous"` is `join-impossible` (a literal one is refused by the type layer first); where it is, omission is `join-undeclared`. Both are structural, neither waivable. konte never derives the join. It is validated over `collectShots`, not `collectArcShots`: the boundary an aside sits at is a cut, and the narrative-only walk cannot see the aside. `join` rides in `projectShotShape`, so an edit ages out both the shot's own part and the root `sequence` part.

**The seam of a long take is ONE frame, and it is the opening keyframe of the shot that owns the boundary.** The shot before it authors no closing keyframe: its last panel moves into that keyframe, and carries `blocking`/`camera` like any other panel (`DirectionIndex.continuedById`, a clock walk over `runOn`, is what `defineAnimatic` reads to lift the landing-frame rule — `assertPanelMoves`, `collectPanelMovement` — and stores as `ShotDefinition.continuedBy`, per lane). Its `lineupTo` is read against no panel of its own: `LineupShot.continuedBy` makes `character-unconsumed` / `slot-order-mismatch` / `subject-unnamed` skip the last-panel reading: `join-lineup-mismatch` (the previous shot's `lineupTo ?? lineup` is this shot's `lineup`) makes the seam's lineup the next shot's, read there against its first panel.

The video answers for the seam: `join-unpinned` fires where the take BEFORE the seam does not pin its `end` to that frame (`checkJoinPins`, over `videoPins` and `shotPanels.firstPanel`), judged where the take before is developed and the board holds the frame, before the take after exists. `VideoShotPins.pins` carries what each pin reaches (the source and its chain through the video's own declarations, so a resize of the frame still pins it) beside `slots`, what its model could (`recordPinInputs` records an empty slot too): a take whose model has no `end` slot is silent, as `panel-unlinked` is. Nothing is demanded of the take after. `load-definition` reads video.tsx for this alone, and only where the direction declares a `continuous`.

A cut along one camera axis is the other boundary the frame does not restart across: an omitted join across two setups sharing a `within` **root**, siblings included — the previous shot's last panel is the new frame's light, size and place. That shot's opening keyframe takes it in any image input of a **`readsPrevPanel`** adapter, found by value: another shot's panel, passed unwrapped. `panel-unlinked` (waivable) fires where such a keyframe took another frame, unless both lineups hold subjects and share none, judged only where both shots are on the board (`panelSeams` / `isAxisCut`); `promptReferenceTags({ prevPanel })` refuses at load a second one, or one the prompt does not name as the source. That axis also splits `undeclared-continuity`, which reads two different cameras only. `axis-unrealized`: a `wide`↔`medium` pair of one axis owes a plate at each end and up to the frame they share, so `plate-unnested` holds them to one master. An aside between the shots breaks the pair.

A `cutin` is declared as `cutin: { setup, lineup, lineupTo?, join? }` on a narrative or graphic shot; `cutin.join`, the seam frame and the previous panel run on the wipe's own lane, and a jump in either frame empties every place.

`docs/SEAMS.md` is every rule above run over fixtures (`seam-doc.ts`, regenerated or the test fails).

## Words

A shot's words split by whether anyone says them. `telop` is unspoken text over the picture, read from the direction by `preview` / `inspect` and passed to no stage. `script` is the spoken lines; a **character** line carries an optional one-line `acting` note — the delivery, hashed with the shot's prose and shown on both review surfaces — and a mob or narration line takes none, the field typed `never` there. Every line demands a cast voice and an `<Audio>` on the animatic shot carrying that line's words, or a `respell()` of them.

`assertScriptVoiced` (`dsl/animatic-builders.ts`) reads `SCRIPT_UNVOICED` per LINE, off the `"spokenText"` reachable from each `stemRef`. A cue yielding none is a recording, and ONE drops the shot back to the whole-shot rule: counting them as one line each refuses a single recording of a two-hander, and this error takes no waiver.

## Casting voices

A `Voice` is `{ id, description }`: `id` is its own exposed `reference:<id>` sample, never the look anchor; `description` is how the member sounds. A `Character` carries an optional one; `direction.narrator` is a bare `Voice`, singular because a `{ narration }` line names no speaker — a piece needing two voices over picture writes `{ speaker }` lines, which anchor to nothing and are unchecked.

`checkCharacterVoices` / `checkNarrator` (`direction-check.ts`) raise `character-voice-missing` / `narrator-missing` on a speaking part with no voice, `*-unreferenced` on one whose sample is not exposed, and `unused-character-voice` / `unused-narrator` on a voice nobody speaks with. All six ride the `characters` class, so they defer until acceptance and then gate every spend; a piece whose lines are subtitles, or whose TTS takes a preset voice name, waives them. `character-voice-empty-description` is structural, never waivable. `reference-id-conflict` covers a voice id colliding with a **roster** id only: two cast members may share one voice id (a narrator who is the protagonist, twins), so a reference id resolves to a LIST of parts — `directionReferenceCascadeTargets` and `referenceRosterEntries` are both many-valued, one accept settles every brief cast on that sample, and the card prints them all.

**The second asymmetry**: a cast voice has its own acceptance gate, `assertVoicesAccepted` (`VOICE_ACCEPTANCE_REQUIRED`), on **both composition stages**. `status` carries that scope through to Next steps as `UnacceptedCastRef.blocks`. The sample is in the cast exclusion set alongside the looks: it is audio, so a **stem-rooted** accept walk (the one that allows audio, signing off what plays) would otherwise reach the sample a line was cloned from.

## Per-part hashing

`directionPartHashes` (`direction-hash.ts`) IS the set of reviewable parts: what it emits is what the review page must offer an Accept for and what the gate demands. Each key is a part's `direction:<field-path>` address; each value hashes everything a reviewer sees on that part. One part per: the root arc (`sequence`), each filled brief field, each policy field (`policy.format`/`policy.lang`/`policy.fonts`/`policy.speech`, always), each shot, each non-root node, each waiver, each roster entry (`setups` included), each cast character voice (`characters.<id>.voice`, only while one is cast) and the narrator (`narrator`). A character entry's hash **excludes** `voice` — the look and the voice are two assets accepted separately, so each must age out on its own edit alone. A shot's hash **excludes** the framing/location its setup carries for the same reason: it hashes the `setup` id, so re-pointing a shot at another frame ages the shot out, while re-describing one frame ages out only that setup's part. `directionPartContents` (`direction-parts.ts`) is the read side — the same key set, holding what each part shows; a part with a hash and no content is one the gate demands and no reader can render, so the two walks must stay in step.

The root `sequence` part is the exception: it hashes `projectShape` (the arc's shape — shots, order, lengths, the roster ids), **not** the prose, so an arc note survives a brief reword. `setups` enters it as `projectSetupShape` — ids **plus** `location`/`framing`, unlike the identity rosters' bare id lists: those two are the piece's size and space cadence. Everything else hashes its own prose too.

Both of the direction's verdicts read this one map. A media-less comment snapshots its part's hash at authoring time and ages out when the part reads differently (see `arch-review-system-guide`); an acceptance snapshots the same hash and ages out on the same edit.

`directionHash` (`projectDirection`) is the whole-direction short-circuit, not a verdict of its own. It holds only because **`projectDirection` is a superset of every part hash's input** — anything a part hashes must be reachable from it, or an edit could leave an acceptance standing that no human gave. When adding a new part hash, extend `projectDirection` too.

## Human acceptance

`direction-acceptance.ts` is the single reader of the acceptance record (the gate, `status`, `doctor`, the review page all go through it). A part's `DirectionPartStatus` is `accepted` (recorded hash matches live), `stale` (recorded but the part changed), or `unaccepted`.

**Reporting and gating are two questions.** `complete`/`blocking` are the page's and `status`'s — every live part at its accepted hash, no orphans. `gateSatisfied`/`gateBlocking` are the spend gate's, and they narrow: the record's `whole` (`{ hash, acceptedAt } | null`) marks that the direction was once signed off end to end, and while it is null the gate IS the full comparison. After it, only `PIECE_WIDE_SECTIONS` — `brief`, `policy`, `waivers` — hold a spend; everything else reaches a human as a panel, a shot or a `reference:<id>` image. `directionGatingSections` is the same split, for the review page's button wording.

Acceptance is recorded **per part**, but on the review page the reviewer accepts **per section** — its boxes. `DIRECTION_SECTIONS` (`address.ts`): `brief`, `policy`, `characters`, `props`, `locations`, `shots`, `waivers`; `directionSectionOf` routes every part address to exactly one, and its total over the part set is what guarantees every part has an Accept somewhere. Two take a foreign prefix: `characters` takes a character's voice part and `narrator`; `locations` takes `setups.<id>`, so the **Locations & Setups** box groups the frames under their place. A section's status is the **weakest** of its parts. The whole arc tree — the root arc (its shape, hashed prose-free by `projectShape`), the child acts, and every shot — is inseparable (splitting a shot re-shapes the arc), so it is one **Flow & Shots** box (`shots`); only the root-arc part's narrower hash still lets an arc note survive a shot's prose reword.

A part accepted and since **deleted** is an **orphan**: the comparison is over the key set, not just hashes. An orphan counts against **its own section** (that box reads not-`accepted` even when empty), because only that box's Accept can drop it (`applyDirectionSectionDecisions` clears a decided box's own orphans, never another's). That is what keeps the gate openable when the last live part of a section is cut. Once `whole` stands, orphans outside the piece-wide sections are **swept** by the next write instead — leaving one would keep `complete` false forever. A deleted **waiver** is no orphan at all (`orphanOwesReview`): removing one only hands its finding back to the machine check, so it never blocks and any write sweeps it, before `whole` too. Waivers sit in `projectNode`, not `projectNodeShape`, so the root `sequence` part does not move either. `isDirectionSpendGateSatisfied` short-circuits on `whole.hash === directionHash` only while `parts` is non-empty; otherwise it walks the full comparison.

There are three writers, and all end on `finalizeAcceptance` — sweep, then re-derive `whole` — so the short-circuit can never outlive the verdict it summarizes, and emptying `parts` (`konte accept direction --off`) is the one way back to never-accepted. `applyDirectionSectionDecisions` is the direction review's: it stamps each decided part at its live hash, carries undecided parts forward, and drops rejected ones. Accept is a toggle (un-toggling revokes); there is no Reject — "what's wrong" lives in the notes. A box with neither an accept nor a live note is named in the submit confirmation, a pause not a block (`pages/preview/review/undecided.ts`).

The second is `applyDirectionPartDecisions`, `konte accept direction[:<part>]`'s: keyed by part address, orphans included — one decided `false` is dropped like any other record, which is how `--off` clears it. Two rules sit in the CLI, not here, and a revoke carries neither: **waivers** are never accepted from it (a waiver is signed off next to the finding it silences, on the page), and nothing is gated on `checkDirection` — the machine's verdict and the human's are the two independent gates the spend order below enforces.

The third writer is the media → direction cascade: an animatic/video shot accept signs off the direction shot and the acts bracketing it, a `reference:<id>` accept signs off the part it anchors — one of the three identity rosters' entries, or the voice part a cast sample belongs to. A `setups` part rides the SHOT cascade, not the reference one: `directionShotCascadeTargets` carries the shot's `setups.<id>` beside its own part and its acts. Without it a setup edit is never re-signed downstream and `complete` stays out of reach for a finished piece. Before `whole` stands it only ever moves a part `stale` → `accepted` (R1); after, it signs off never-read parts too. Touching either: read `references/cascades.md`.

The gate order at spend time (`load-definition.ts`): `assertDirectionGate` (structural + findings) → `assertDirectionAccepted` (`DIRECTION_ACCEPTANCE_REQUIRED`, naming each blocking part) → `assertCharactersAccepted` → `assertVoicesAccepted` (video only). The reference stage is exempt from the acceptance gate.

## Policy fields

`format`, `fonts` and `speech` are machine-checked, each in the acceptance hash (editing one re-blocks) and each its own feedback part (`direction:policy.<field>`), and each enforces only what konte can check:

- `policy.format` (`{ fps, size: { megapixels, delivery } }`) — the working canvas is **derived, not authored**. `deriveCanvasBase` (`core/canvas.ts`) resolves the budget against the delivery's aspect and returns the nearest 32-grid size, ranking aspect error above area error. `resolveDirectionFormat` is the one place that runs it; `DirectionIndex.format` is the resolved form (`ResolvedDirectionFormat`) and every reader holding a bare `Direction` instead (`projectFormat`, `direction-parts`, `patch.ts`, the review page) goes through it. `assertCanvasFormat` checks only what is authored — a positive `delivery`, a `megapixels` under `MAX_MEGAPIXELS` (unit-slip guard), a positive finite `fps`. No grid check, no aspect check: neither number is written by hand. `DELIVERY_UPSCALE_REQUIRED` fires only above `UPSCALER_REQUIRED_ABOVE` (1.2×). **The hash takes the derived canvas, never the budget**, so a budget edit landing on the same canvas ages nothing out. The grid step the canvas lands off by is cropped from the centre at export, never upscaled. A reference sheet is sized off the canvas' **long edge**: portrait for a character, a 2:1 master at twice it for a location, square otherwise. Changing the derivation moves every existing piece's canvas and stales what was built on it, so a change needs a version pinned in `direction.ts` to opt into — there is none today.
- `policy.lang` (one of the closed `LANGUAGES`, a script or region may ride along) + `policy.fonts` (Google Fonts family names) are the typesetting all three stages read, carried as one `Typography` on `DirectionIndex` — `lang` on the document root, the fonts as one stylesheet `<link>` and the composition body's fallback stack. Preview and capture load the faces from that link; the export also embeds them, HyperFrames resolving every `font-family` in the HTML into `@font-face` data URIs. `checkTypesetting` raises the waivable `fonts-undeclared` when `fonts` is empty and `scriptOf(lang)` — the tag's script subtag, else the language's `DEFAULT_SCRIPT` — is in `SCRIPTS_NEEDING_A_DECLARED_FACE`.
- `policy.speech` (`"none"` / `"no-dialogue"` / `"free"`) raises the waivable `unexpected-script` finding on a shot whose `script` contradicts it (`none` forbids any line, `no-dialogue` forbids spoken lines but allows narration, `free` imposes nothing).
