How the files `konte workspace new` writes are authored and assembled.

## The tree mirrors what it produces

```
src/cli/templates/workspace/       ← konte workspace new
  adapters/  dot.konte/mod.ts  tsconfig.json  dot.agents/  …
  videos/
    blank/  kitchen-sink/          ← konte video new <name> --template <one of these>
```

- A video template's `import … from "konte/workspace/adapters/comfy/x.js"` resolves to the same file here as in a real workspace — `konte/workspace/` is the workspace root.
- `embed-templates.ts` walks `workspace/` once — a key under `videos/<name>/` is that video's template, everything else is the workspace scaffold.

## Naming convention

- A `dot.` prefix becomes `.` on write (`dot.konte/mod.ts` → `.konte/mod.ts`) — a real `.konte/` in the dev tree would collide with the repo's own gitignore.

## Generated files

- `workspace/dot.konte/mod.ts` (the user-project DSL type declarations) — `bun run build:generate-template-mod` after changing DSL types/builders.
- The embedded template assets — regenerated by `bun run build`.

## Where to add a file

- Shared by every video (agent setup, adapters, config) → `workspace/`.
- One video template's content → `workspace/videos/<name>/`.
- A whole new video template → a new directory under `workspace/videos/`.
- A dev-only video template → also in `DEV_VIDEO_TEMPLATES`; only a release binary (`compile-binary.ts --release`) drops it. `kitchen-sink` is the DSL surface `check:templates` covers; grow it with the DSL.
- A dev-only skill → also in `DEV_SKILLS`; likewise dropped only from a release binary.

## Managed files and agent settings

- Only `workspace new` / `workspace setup` sync; `workspace setup` refuses with `KONTE_OUTDATED` when `konte.version` names a newer konte, so going back to an older konte is lowering `konte.version`. Every other command writes nothing; a compiled konte refuses with `KONTE_OUTDATED`, else with `WORKSPACE_SETUP_REQUIRED` when the lock's template hash (managed files, bundled adapters, agent settings, `.gitignore`) or its `root` differs, a managed file or agent setting is missing, or the compiled konte's `.konte/bin` link does not resolve.
- `.claude/settings.json` is overwritten — user customizations belong in `.claude/settings.local.json`, left untouched; other agent settings also fill missing defaults. These settings are gitignored.
- The konte MCP/LSP launch fields and the `.konte/bin` PATH lead are regenerated — Codex through `shell_environment_policy.set.PATH`, Claude Code through a `SessionStart` hook appending an `export PATH` line to `$CLAUDE_ENV_FILE`, since its `env.PATH` never reaches the Bash tool.
- Launch paths always name `.konte/bin/konte`: a compiled konte running from elsewhere (brew, a copied build) links itself there — to the `PATH` entry resolving to it, if any — except on Windows, and never over a real file `setup.sh` placed.
- `konte.version` is not a template: `template-sync.ts` writes it at the workspace root once every file is written. It is committed; the lock's copy of the version is not.
- A bundled adapter (`BUNDLED_ADAPTERS`, every file under `adapters/`) is overwritten while present; a missing one is added only when the release that first shipped it is newer than `konte.version`, so a removed one stays removed. That release is `src/cli/templates/adapter-releases.json`'s, stamped by `release:version`; an unstamped adapter is unreleased and always added. `workspace setup` leaves adapters to the sync.
- The lock's `files` records the bundled adapters and `.konte/guides/` files a sync left in place. A recorded one the template no longer holds is deleted unless a workspace `.ts`/`.tsx` outside dot-directories and `node_modules`, or `konte.config.json`, names it (a name inside another file being deleted does not count); a named one is kept, reported, and stays recorded. A lock without `files` deletes nothing.
- A managed file (`MANAGED_TEMPLATES`) must be a workspace file — `syncWorkspace` writes every managed key relative to the workspace root, so a managed key under `videos/` would land a video's file at the workspace root on the next upgrade. `embed-templates.ts` asserts this.

## Type-checking

- `bun run check:templates` runs `tsc` once over `workspace/tsconfig.json` — the shared adapters and every video template together, as a real workspace is checked.
